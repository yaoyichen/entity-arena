# Entity Resolution Fine-tuning — Client Data Contract (v0.1 draft)

> Purpose: define what the client provides and what INF returns, so that the
> train → evaluate → deploy → score pipeline runs as a one-click service.
> Precedent: all numbers below mirror the Febrl3 pilot in this repo
> (1,600 training entities / 10,478 positive pairs / 10,998 hard negatives
> were enough to reach precision 1.0 / recall 1.0 on the case village).

## 1. What the client provides

### 1.1 Records file (required)

CSV or JSONL, one row per record, UTF-8.

| Column | Required | Notes |
|---|---|---|
| `record_id` | yes | Unique, stable, non-empty. Duplicates are rejected at intake. |
| `<field_1..n>` | yes | Any number of business fields. Free text or structured. Missing values: leave empty — do NOT pad with placeholders (missingness is signal, per our Febrl pipeline). |

### 1.2 Labels — exactly one of the two formats

**Format A — entity ID column (preferred, cheapest)**

Add one column `entity_id` to the records file: records sharing the same
`entity_id` refer to the same real-world entity. Febrl-style. Positive pairs
are derived automatically (all within-entity pairs).

**Format B — pair-level label file**

Separate CSV: `record_id_a, record_id_b, label` with label ∈ {1 (same
entity), 0 (different entity)}. Use when entity IDs are not available but
confirmed match/non-match pairs are.

Minimum viable annotation budget (from the Febrl pilot): **~1,500–2,000
labeled entities** (or ~10k labeled positive pairs). Hard negatives are
generated by us automatically (same-surname / same-locality / same-DOB
different-entity records) — the client never labels negatives.

### 1.3 Field metadata (required, small YAML or table)

For each field, the client declares a role:

| Role | Meaning | Example |
|---|---|---|
| `embedding` | Serialized into the model input | name, address, DOB |
| `unique-key` | Hard-constraint field — NEVER enters the embedding; used only by the logic layer for consistency checks (conflicting keys veto a link regardless of score) | SSN, tax ID, passport no. |
| `ignore` | Excluded | internal row numbers, update timestamps |

This split mirrors the two-stage architecture presented on 2026-11-10
(scoring engine + logic engine). If no field is marked `unique-key`, the
logic layer is simply disabled.

Optional per field: normalization notes (date format, casing, transliteration).

## 2. What we do with the data (fixed, no client effort)

1. **Intake validation** — `record_id` uniqueness, label referential integrity,
   empty-file / single-entity guards. Failures are reported, never silent.
2. **Entity-level train/test split** (80/20, seed fixed) — all records of one
   entity stay on one side; zero leakage. Pair-label data is split by pair.
3. **Training package build** — BEIR-style queries/corpus/qrels + auto hard
   negatives (rules: shared rare attribute values, different entity).
4. **Serialization** — `field: value | field: value | …` per the declared
   field order; `unique-key` and `ignore` fields excluded.
5. **Fine-tune + evaluate on the platform** — report recall@k and pair-level
   precision/recall/F1 on the held-out split, θ chosen by F1 scan, with the
   same honest-metrics format as the Febrl pilot (every number names its
   protocol; no mixing of evaluation regimes).
6. **Deploy** — `/v1/embeddings` service + published θ and decision rule.

## 3. What the client receives

1. Deployed embedding endpoint (scoring engine) + θ threshold + decision rule;
2. Evaluation report on their held-out split (before/after fine-tuning);
3. The same offline demo page re-pointed at their data (network view,
   scoreboard, playground) — their records, our pipeline, zero extra cost;
4. MCP tools (`er_score_pair` / `er_find_records`) for integration trials.

## 4. Process

| Step | Who | Output |
|---|---|---|
| 1. Schema review | both | field-role table agreed (§1.3) |
| 2. Pilot: client sends a sample (~5k records + labels) | client | we run the full pipeline, return the evaluation report + demo page on their data |
| 3. Full run | INF | deployed service + report |
| 4. Optional: logic-layer rules tuned on `unique-key` fields | both | veto rules documented in the decision rule |

## 5. Data handling

- Data stays within the agreed training platform tenancy; no third-party
  sharing; `unique-key` fields can be hashed before delivery if the client
  prefers (hashing preserves conflict detection — equality is all the logic
  layer needs).
- Vectors and tokens never leave the client tenancy / this repo's convention:
  tokens live outside the repository, embeddings are sampled to `.tmp/` only.
